Exposed the tokenizer through typed generational handles: load, load_path, encode, decode, token_to_id, info, and close, with the extension.toml manifest, module.mlpl facade, mlplunit record-shape test, loader contract tests across dynamic and static providers, and a just hftok-check recipe running a real MLPL round trip. The work order's one-argument load(path) is load_path, confining the read to the named absolute file's own directory; nothing ambient is consulted and the rule is documented rather than configured. Running it end to end found two things unit tests could not: MLPL numeric arrays are f64, so i64 ids arrive back at decode as f64 after a round trip through the interpreter, and decode now accepts both while refusing non-whole values rather than truncating; and this repository's own SDK could build an i64 array but not read one back, so I added ArrayView::as_i64 here rather than filing a request. Handle safety is proven by constructing foreign, wrong-type, never-issued-generation, and closed handles and checking every call path rejects each. 28 crate tests pass, clippy clean after fixing three lints including converting a lossy cast to a checked one. Full gate passed with PASS pre-commit after fixing a rustfmt diff in the new host binary.
